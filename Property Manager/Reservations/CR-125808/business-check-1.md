## Checked and kept (no row)

- **State machine and deferral consistency:** Draft → Confirmed → Cancelled, Converted reserved but unreachable until D1; a Confirmed unit always has a way back (A7), an expired Confirmed reservation is warn-only (BR-7, Q4) and still cancellable, so no unit is stranded in Reserved. Delete only in Draft (BR-1) touches no unit. Pass.
- **Confirm guard (A6):** status check + write in one command / transaction is the only race guard needed; two drafts on one unit are allowed, the second Confirm fails on status. Pass (row 3 fixes the predicate).
- **Accounting deferral (D3–D5, D7):** `Settings.md` BR-16 says the tenant’s 1210 / 2330 sub-accounts are created at first reservation confirm (D31); the Logistics endpoint already creates them at customer creation, so the deferral leaves no account gap. Deposit and collected amount live on the reservation only, collected is always 0, so cancel with no refund is consistent. Pass.
- **Defaults (A1):** expiry = today + `ReservationValidityDays` (null → 14) = `Settings.md` BR-17 / AC-4 and field 16; start = today + 15 (field 22); years 1; payment method bank transfer in (field 26). Pass.
- **Project filter (A3):** rent projects = `ProjectInvestmentTypeList` contains `InvestmentType.Renting = 2`, leaf projects only, project not stored (field 19). Matches the `GetSaleProjectsQuery` / `GetAvailableSaleUnitsQuery` pattern. Pass.
- **Tenancy / branch:** `Pm_*` tables carry no `BranchId`; PM data is per tenant DB (CR-125716 check row «Uniqueness scope»). The customer is a Logistics row of the same tenant; the only branch-shaped fact is the sales organization, handled in row 4. No cross-tenant reach. Pass.
- **Permissions (A10):** View / Add / Edit / Delete / Confirm / Cancel under module 957; Confirm and Cancel as separate permissions match the house pattern for document actions. Pass.
- **Payment method:** stored as an int on the reservation only; no receipt is created (D4), so no CashControl entity type is implied yet. Pass.
