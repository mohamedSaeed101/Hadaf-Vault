# CR-125486 — Decisions (engineer, plan gate, 2026-10-18)

- **Q1 Parent cost center:** one parent cost-center dropdown on the import screen. It is required only when a row asks for a cost center, and every auto cost center goes under it. (Recommended option.)
- **Q2 «اثبات الإيراد» (ProofOfIncomeAndExpenses):** **remove it from both the Projects and the Properties screens**, and keep it out of the import. "We will always look at the settings." **Keep the `Pm_ProofOfIncomeAndExpenses` lookup table.**
  - Read as: remove the field from both forms, both create/update commands and their DTOs.
  - The `Pm_Project` / `Pm_Property` columns stay, with no drop and no migration. New rows get the DB default (1), or 1 set in code where the column has no default.
  - The settings field itself is not built in this CR. Nothing reads the value for posting today.
  - This **widens scope**: the Properties screen + `CreateProperty` / `UpdateProperty` / `GetPropertyById` / `GetProjectInfoById` are now in the plan.
- **Q1 (confirmed by v2):** the parent dropdown lists active **non-leaf** cost centers only. The choice is kept for the next file in the same session.
- **Q3 Activity (final, engineer 2026-10-18):** keep the user-maintained `Pm_ProjectActivities` as it is (no new table, no seed, the popup stays). Template column 25 holds the activity **id**, not the name. Blank = no activity, never derived from the investment type. An id that is not in the tenant's list is an error. The "Template columns" tab lists the tenant's activity ids and names so users can copy them. (This overrides v3's "by name".)
- **Q5 (v3):** a blank status stays blank, the same as the screen. An unknown status is an error (AC-12).
- **Q8 (v3):** the auto cost center is a **non-leaf** cost center (`IsLastNode = false`) with both names (a GL overload) and is linked to `Project.CostCenterId` (AC-11). The parent list holds active non-leaf cost centers **with no transactions**. The API checks the parent once and rejects the whole import if the check fails.
- **Q9 (v3):** use the screen's cost-distribution list exactly as it is today. «نسبة لمساحة العقار / نسبة يدوية لكل عقار» is a **future change to the Projects screen** (desktop parity), not part of this CR. Once that lands, the import follows the new list automatically.
- **Q4 Uniqueness (engineer 2026-10-18):** **import + Projects screen.** Number, name and second name are unique. The import checks against the DB and within the file. The `CreateProject` and `UpdateProject` commands get the same check, from one shared rule, and update excludes the project itself. No DB index. **Existing duplicates on tenants are not checked or handled** (the engineer's call): if one exists, editing it shows the duplicate error.
- **Q6 Limits:** 1000 rows and 5 MB per file. The front checks before upload, and the API rejects more than 1000 rows.
- **Q7 Menu:** a new group «أدوات المشاريع والعقارات» / "Projects & Properties Tools" under the Property Manager settings. «استيراد المشاريع» is module **934**. CR 125487 (import units, 935) goes in the same group.
- **Q10 Cost center code:** parent code + the next free child sequence, the same as the GL / Machine pattern (51, 52, …). Always digits, and AC-7 still holds. The project number appears only in the name. (This overrides v3 BR-9 "parent code + project number".)
- **Q11 «اثبات الإيراد» columns (engineer 2026-10-18):** **drop the columns.** Remove `Pm_Project.ProofOfIncomeAndExpenses` and `Pm_Property.ProofOfIncomeAndExpensesId` (and its FK and default). **Keep the `Pm_ProofOfIncomeAndExpenses` lookup table** and its reference-data script.
  - This is a destructive schema change: existing values are lost. A dacpac publish with `BlockOnPossibleDataLoss` will stop, so the drop needs the publish profile / a pre-deploy decision (handled in DB phase 1).
  - It is also a **breaking API contract change**: the field leaves the project and property DTOs and commands. The front and API must deploy together.
- **Split of the «اثبات الإيراد» removal (engineer 2026-10-18, in CR-125487 Q13):** the **property** side moves to CR-125487: `Pm_Properties.ProofOfIncomeAndExpensesId` + FK, `Property` / `PropertyPoco`, the Create/Update Property commands, `PropertyDto`, the property queries and the Properties form. **This CR keeps only the project side:** `Pm_Project.ProofOfIncomeAndExpenses` + its DF, `Project` / `ProjectPoco`, `ProjectDto`, `ProjectInfoDto`, and the Projects form. The plan rows 1, 2 and 9 still list the property parts; take them out before phase-loop runs.
- **Note from CR-125487 (2026-10-18), not yet decided for this CR:** the deployer (`DB.Deployer\Operations.cs`) hard-codes `BlockOnPossibleDataLoss = true`, so dropping a column that holds data stops tenant upgrades. For `Pm_Properties.ProofOfIncomeAndExpensesId` the engineer chose **`INT NULL` + drop the FK now, drop the column later**. `Pm_Project.ProofOfIncomeAndExpenses` (plan row 1) hits the same block and needs the same call.
- **Q15 Amenity client drift (engineer 2026-10-18):** fix it in this CR. `amenity-main-grid` moves from the string `Serves` to the int amenity-type ids, following backend commit 93ebc16f3b "refactor amenity types". Call it out in the PR as client-drift fallout.
- **Rule bent (review-1 S2):** `Pm_ProjectImportLog` uses `DATETIME` for ImportDate, CreatedOn and LastModifiedOn instead of `db-rules.md` §Data Types `datetime2(3)`, to match the sibling `Pm_` tables (Pm_Project uses DATETIME for the same audit columns). Cite it in the PR.
- **Q13 (engineer 2026-10-18): keep the column, drop it later.** This **overrides the DB half of Q11**. `Pm_Project.sql` was reverted to base, so `ProofOfIncomeAndExpenses` (DEFAULT 1) stays in this release. The code still removes the field (no EF mapping, DTO or form), and new projects get the default. A follow-up CR drops the column once DB.Deployer can allow that data loss. Review-1 row S1 is resolved by this.
- **Q16 (engineer 2026-10-18): المركز is a lookup.** Matched by name (ar/en) against `ACFX_Center`, the same list as the screen. Blank = no center; an unknown name is an error. v3 field 16 changed to «قائمة». The template-columns tab says so (`_CenterNote_` ar + en, TypeKey List).
- **Q17 (engineer 2026-10-18): fix the shared message.** `ProjectNameSecondLanguageRequired` is now «الاسم بالغة الثانية إلزامي» / "Second-language name is required" (Resource.resx, Resource.en.resx and the Designer comment). The Projects screen shows the new text too, and the old typo «المشروغ» is gone.
- **Q13 reversed (engineer 2026-10-18): drop the column in this CR after all.** `Pm_Project.ProofOfIncomeAndExpenses` + `DF_Pm_Project_ProofOfIncomeAndExpenses` are removed from `Pm_Project.sql` again, so Q11 stands in full. Reason ([[followup-drop-proof-column]]): real tenant upgrades go through AccessControl `DatabaseOperations.UpgradeDatabase` with `BlockOnPossibleDataLoss = false` (lines 120-130), and the stage pipeline passes False. `DB.Deployer` (true) has no consumer. Existing values are lost on upgrade, which the engineer accepted under Q11. Shared test tenants (Sabreen) still have the column until a publish applies the drop.
- **Q3 changed again (engineer 2026-10-18, after the video): activity is entered BY NAME, not id.** The cell must match the name (Arabic or English, normalised) of an activity that exists in the system's `Pm_ProjectActivities`. Blank = no activity. A name that isn't in the list is an error, and a name matching more than one activity is an "ambiguous" error. This matches v3 field 25 and AC-13. The row DTO field is renamed `ProjectActivityId` → `ProjectActivity`, and the template-columns tab lists the tenant's activity names.
