## Method

- **Before (legacy):** the xsd CommandText verbatim, run through `sp_executesql` with the typed-DataSet parameter types.
  - String parameters have xsd `Size=0`, so they are passed as `nvarchar(max)`.
  - Parameter values are the ones the rpt classes pass:
    - from = date 00:00:00, and to = date 23:59:59.997.
    - A: `@CurrencyId`, `@JournalRevise`, `@JournalTypeList` and `@AccountList` are NULL.
    - B and C: `@CurrencyId` and `@AccountList` are NULL.
  - B runs twice, with `@IsEnglish = 1` and with `@IsEnglish = 0`.
  - Where the SQL came from:
    - R2–R4: the vault note "Legacy - Estimated Budget (A-B-C)", sections A.4, B.4 and C.4. `gen.py` confirmed that each one equals its xsd CommandText on `origin/Master_Stable` once whitespace is normalised.
    - R1: the vault copy is re-indented and drops the `AS Acc_ConvertIntListToTable_2` alias, so the script uses the CommandText from `dsPeriodBalanceReport.xsd` on `origin/Master_Stable` itself. It has the same semantics.
- **After (new):** the text of each TVF body between `RETURN (` and the final `)`, verbatim, run through `sp_executesql` with the TVF's own parameter list. There are no substitutions.
- **Checks per comparison:**
  - row counts
  - `before EXCEPT after` and `after EXCEPT before`
  - duplicate-aware: GROUP BY every compared column with COUNT(*) on both sides, then EXCEPT both ways
  - SUM of every money column. Both sides are stored as `decimal(38,10)` from `money`, so the comparison is exact.
  - order:
    - RowNo is 1..n, and is non-decreasing on the legacy sort key: AccountNo for R1 and R2, AccountNo then Mnth for R3, AccountNo then DayDate for R4.
    - Where the legacy query has an ORDER BY (R2, R3, R4, all `ORDER BY AccountNo`), the legacy arrival order is compared with RowNo position by position on AccountNo.
    - R1 has no legacy ORDER BY, so only the TVF ordering is checked for R1.
- **Compared columns:** the legacy column set.
  - Ignored, because only the TVF has them: RowNo, AccountId (R1, R3, R4), CurrencyNameArabic (R1), MonthNameArabic in the English run, and MonthName in the Arabic run.
  - R3: `RTRIM(NameMonth)` from the `@IsEnglish = 1` run is compared with `MonthName`, and from the `@IsEnglish = 0` run with `MonthNameArabic`.
- **Result-set metadata** (`sys.dm_exec_describe_first_result_set` on both texts): every compared column has the same type on both sides. The one exception is the intended R3 `NameMonth nvarchar(7)` → `MonthName nvarchar(3)`, because the TVF trims the trailing space.
- **Negative controls:** only the new side's parameters are perturbed. All four were detected.

  | Tenant | Perturbation (new side only) | Effect |

  | ELGHONEIM | R1 SP 30, branches NULL → `2` | 1,728 → 674 rows, 1,054 rows B−A, sums differ |

What these cases exercise:
- **Year fold.** The month list repeats month numbers across years, and every repeat becomes an identical duplicate row.
  - dbriyadh 22 months: months 2–10 twice plus month 11 once, 19 rows.
  - Rusasnew 16 months: months 7–10 twice, 8 × 68 accounts = 544 rows.

  The duplicate-aware check shows that both sides carry the same multiplicity.
- **Day-of-month drift.** From 2024-01-31 the recursive month steps go 02-29, 03-29, … 2025-03-29, so March 2025 still falls before the 03-30 bound. The result is 6 month entries × 68 accounts = 408 rows. Without the drift it would be 340. The TVF keeps the recursive CTE (decisions.md), so the two sides agree.
- **Negative budget.** The ACCFLEX-ERP cc `28,13` cases include the −1 budget on account 2172, cost center 13. They show that DeviationPercent divides by the signed Budget on both sides.
- **Budget cost centers.** Rusasnew and dbriyadh have no cost center on any budget row. The legacy cost-center filter keeps only budgets in the list, so a cost-center list empties both sides there. ACCFLEX-ERP covers budgets that do carry cost centers.

## Data limits (what this cannot prove)

- **R2 budgets:**
  - ELGHONEIM's only two weekly budgets have the value 0, so ShowZero 0 returns 0 rows there.
  - ACCFLEX-ERP has one weekly budget (15,000, account 2108, branch 1026, no cost center). It is the only non-zero R2 budget row exercised.
- **R4 PeriodBalance** is 0 on every row. The tenant's only daily budget (account 67 / 10101, 10,000, branch 3) is on a leaf account whose only journal action is voided: credit 5,000 on 2026-04-08, with `Void = 1` on both the action and the journal. The `Void = 0` filter therefore drops it on both sides. Budget, Deviation and DeviationPercent are non-trivial; the PeriodBalance path is proven only as 0 against 0. Per the brief, no other tenant on db-all has an `IsFixedDaily` budget.
- **R3 budgets:**
  - Rusasnew has 816 budget rows, but only 4 of them are non-zero (20,000 in total). Most rows compare budget 0, which gives DeviationPercent 100.
  - dbriyadh has a single budgeted account.
- **Budget branches:** no budget row has a NULL branch, and no `Acc_AccountBalance` row has a NULL branch on these tenants. The "NULL list includes NULL-branch rows" quirk is therefore only proven by reading the code (the WHERE clauses are verbatim).
- **R3 range direction:** a range whose start month is later than its end month, such as Nov..Feb, makes the legacy `BETWEEN MONTH(from) AND MONTH(to)` return no budgets. No such case was run; the clause is verbatim.
- **Compatibility level:** Rusasnew runs at compatibility level 120. The harness avoids STRING_SPLIT, and both sides run there unchanged.
