## Method

### Legacy side (L)

- The English typed-DataSet `CommandText` is used verbatim. It is read from the xsd files on `origin/Master_Stable`; the main checkout's copies show no diff against that branch.
  - The files are `IncomeStatmentActivityBudgetYearToDate\dsIncomeStatmentActivity.xsd`, `CostCenterIncomeStatementBudgetComparison\dsCostCenterIncomeStatementBudgetComparison.xsd` and `IncomeStatmentPerMonth\dsIncomeStatmentPerMonth.xsd`.
  - Once whitespace is normalised, all 13 queries equal the SQL blocks in [[Legacy - Income Statement family (1-5)]].
- The queries run through `sp_executesql` with the xsd parameter types. String parameters have xsd `Size=0`, so they are passed as `nvarchar(max)`.
- Parameter values are the ones the rpt classes pass:
  - **R1:**
    - `ActivityIncome.Fill(@AccPeriodList = sub-period id, revised, journalTypes, @CostCenterList = list, @BranchList = NULL)`
    - `Acc_IncomeStatment.Fill` with the same arguments
  - **R2:**
    - `BranchIncomeState.Fill(sp, revised, journalTypes, NULL, branches)`
    - `Acc_IncomeStatment.Fill(sp, revised, journalTypes, NULL, branches)`
  - **R3:** `ComparisonActivityIncome.Fill` and `Acc_ComparisonIncomeStatment.Fill`. Both take `(fromMonth, toMonth, from, to, revised, journalTypes, costCenterList)`.
  - **R4:** `ComparisonBranchIncome.Fill(..., branches)` and `Acc_ComparisonIncomeStatment.FillByBranch(..., NULL, branches)`.
  - **R5:** the six `Acc_IncomeStatement_*PerMonth.Fill` queries, each called with `(0, toMonth, from, to, revised, journalTypes, costCenterList, branches)`.
- Dates follow the MVC controller's month mapping. The rpt classes set `to` to 23:59:59.997.
  - `true` → months 1..6, Jan 1 to Jun 30.
  - `false` → months 6..12, Jun 1 to Dec 31.
  - `null` → months 1..12, Jan 1 to Dec 31.
  - R5 always uses fromMonth 0.
- An empty list is passed as NULL, because ASP.NET Core binds an empty query value to null.
- The **print-time rollups** are rebuilt over the legacy rows in SQL inside the harness. These are the expected values the TVF's synthetic rows are compared against:
  - **R1/R2:**
    - `GrossProfit`: one row per `CostCenterNo` / `BranchCode`, the Group SUM of the 10 Cal* columns. This is the layout's GroupFields.
    - `GrossProfitPercent`: one row per group, all 0. `revenu[i]` is set only for a value below 0, and every value is ABS.
    - `TotalGrossProfit`: the Report SUM of the Cal* columns.
    - `OtherAccountType`: the `Acc_IncomeStatment` rows with types 1/2 removed, as `Detail2_BeforePrint` cancels them.
    - `NetProfit`: the Report SUM of `Acc_IncomeStatment.Cal*` over **all** rows, including types 1/2. This is the TVF's reading of open question 8. The "excluding 1/2" variant is printed as INFO; see the Observations.
  - **R5:**
    - `GrossProfit` = OI − OE.
    - `NetProfitBeforeTax` = OI − OE − OtherExp + OtherInc − Admin.
    - `NetProfit` = NPBT − Taxes.

    These are whole-range sums of `SubItemBalance` per category, and they include Taxes' NULL-month rows.

### New side (N)

- The text of each TVF body between `RETURN (` and the final `)` is run verbatim through `sp_executesql` with the TVF's own parameter list. It is taken from the `cr125290` worktree, and nothing is substituted.

### Comparison

Both sides are projected onto one shape:
- `RowType`, `DimId`, `DimNo`, `DimName`, `TypeId`, `TypeName`, `TypeNameAr`, `SubItem`, `MonthNo`, `MonthName`, `V1..V10`.
- The comparison runs per part:
  - R1/R2: AccountType, GOP, OtherAccountType, Totals.
  - R3/R4: Dimension, Summary.
  - R5: SubItem, Totals.
- **R1/R2:**
  - AccountType rows compare `DimensionId`, `DimensionNo`, `DimensionName`, the En and Ar type names and all 10 values.
  - GOP and % rows compare `DimensionNo` plus the values. The TVF's `MIN(DimensionId/Name)` on these rows is not compared; see Observation 2.
  - Total and NetProfit rows compare the values only. Captions are not compared.
- **R3/R4:**
  - The `Dimension` section is compared to the English Fill of ComparisonActivityIncome / ComparisonBranchIncome. `Budget` maps to SubItemBudgetValueBalance and `Actual` to SubItemActualBalance.
  - The `Summary` section is compared to Acc_ComparisonIncomeStatment Fill / FillByBranch. `Budget` maps to BudgetValue and `Actual` to AcutalValue.
  - Month is compared on `MonthNo` and on `RTRIM(monthname)` = `MonthName`. Every tenant runs at `us_english`, so `DATENAME` is English.
- **R5:**
  - SubItem rows compare `MainItemId` (the category query the row came from), `MainItemName` (En), `SubItemName`, `MonthNo`, `MonthName` and `Balance`.
  - Total rows compare `RowType` and the value.
- `MonthNameArabic`, `OrderInReport`, `IncomeStatmentSubItemId` and the captions exist only in the TVF, so they are not compared. D2 makes English the reference.
- Money is held as `decimal(38,10)` on both sides. The legacy side is `money` and the TVF side is `decimal(19,4)`, so the comparison is exact.

### Result-set shape

`sys.dm_exec_describe_first_result_set` runs on all 18 texts, and the harness's positional `INSERT ... EXEC` column lists follow its output. This includes the per-query column order of R5, which differs from query to query.

### Synthetic budgets (supplement, dbriyadh only)

A probe of all 106 accessible tenants on db-all found the following:
- Only **Rusasnew** has budgets on account types 1/2. It has 4 rows: type 2, branch 2, no cost center.
- **No tenant has a type 1/2 budget with a cost center.**

With real data, the R3 `Dimension` section is therefore always empty, and the R1 per-cost-center budget columns are always 0.

To exercise those paths without writing to the database, the harness works on a session copy:
- It copies `Acc_AccountBudget` into a session `#Acc_AccountBudget`.
- It adds 11 account / cost center pairs × 18 ids (1..12 used as months, and 1, 14..19 used as sub-periods), all on branch 2.
- In SYN cases, it runs **both** the legacy text and the TVF body with `Acc_AccountBudget` textually replaced by `#Acc_AccountBudget`.

The added pairs are:
- type 2: (1060,43), (1142,43), (116,49), (1060,45), (117,55)
- type 1: (33,49), (33,43), and (33,34) with a negative budget
- type 4: (50,49)
- (1159,49), which has a budget but no actuals in that cost center
- (33,NULL), a budget with no cost center

They also include:
- a same-value duplicate on branch 3, for the legacy `SELECT DISTINCT` collapse
- a different-value duplicate on branch 3

This proves that the legacy logic and the TVF logic agree on these shapes. It does not prove anything about real budgets.

   - `CAST(DimensionName AS NVARCHAR(250))` is at line 209 of both `Acc_IncomeStatementCostCenterPeriodBudgetReport.sql` and `Acc_IncomeStatementBranchPeriodBudgetReport.sql`.
   - The source columns are `Acc_CostCenter.CostCenterName nvarchar(300)` and `Acc_Branch.BranchName nvarchar(500)`, and the legacy print shows the full name. A CAST truncates without an error.
   - The longest names on the tested tenants are 86 and 34 characters, so the truncation never happens here.
   - The plan's contract says `DimensionName NVARCHAR(250)`. R3/R4 do not cast, and return 300 / 500.
   - **Proposed fix:** cast to `NVARCHAR(300)` in R1 and `NVARCHAR(500)` in R2, or drop the cast as R3/R4 do. Keep the entity's max length in line.
2. **R1/R2 GOP and % rows take the name of the lowest id.**
   - The rows carry `MIN(DimensionId)` and `MIN(DimensionName)` per `DimensionNo` (lines 166 and 175).
   - The legacy group header prints the name of the first row in `CostCenterNo` / `BranchCode` order.
   - The two can differ only when two cost centers or branches share a number. There are 0 such duplicates on the tested tenants.
   - The difference is cosmetic and does not affect the numbers.
3. **Open question 8, NetProfit with or without types 1/2, changes the numbers.**
   - The TVF includes the cancelled type 1/2 rows, and parity was run on that reading. The INFO lines show what the other reading would give:

     | Case | Incl. 1/2 | Excl. 1/2 |
     |---|---|---|
     | Rusasnew SP 13, jt 5,6, PeriodBalance | 22,122.3716 | −104,646.00 |
     | ACCFLEX-ERP SP 1020, PeriodBalance | −10,030.0006 | −10,000.00 |
     | ACCFLEX-ERP SP 1020, YTD | −163,582.3046 | −120,968.6737 |

   - SQL cannot prove which reading DevExpress uses, so the P6 app check should confirm it against one live MVC print of a case where the two differ, such as ACCFLEX-ERP SP 1020.
4. **The legacy adapters cannot take a NULL journal-type list.**
   - Every adapter here declares `@JournalTypeList AllowDbNull="false"`, so a legacy Fill throws `ArgumentNullException` when `journalTypes` is null.
   - The new screen sends `''` / NULL to mean all types. Parity passes NULL to the legacy SQL for "all", which matches what the SQL does.
5. **Closing entries zero out most `Acc_IncomeStatment` rows.**
   - On Rusasnew and dbriyadh, the leaf income accounts net to 0 inside each period. For example, Rusasnew SP 13 shows debit = credit for types 1, 2 and 4.
   - So OtherAccountType and NetProfit are 0 unless a journal-type or revised filter drops the closing journal.
   - The parameter sets with jt filters cover this: Rusasnew #3 and #7, dbriyadh #3, and ACCFLEX-ERP SP 1020.

## Data limits (what this cannot prove)

- **Budgets on types 1/2 with a cost center** exist on no tenant of db-all. All 106 accessible tenants were probed. The R3 Dimension section and the R1 per-cost-center budget columns are proven only on the synthetic copy.
- **Real type 1/2 budgets** exist only on Rusasnew: 5,000 on each of sub-periods / months 1..4, type 2, branch 2.
  - They drive R2 AccountType budgets: PeriodBudget at SP 1, YTD at SP 13.
  - They drive the R4 Dimension rows.
- **R3/R4 summary budgets** on dbriyadh and ACCFLEX-ERP are type 4 only (Administrative).
- **Revised journals** are sparse: dbriyadh 2025 has 6, ACCFLEX-ERP has a few. Revised = true cases often compare small or empty sets.
- **The `SELECT DISTINCT` collapse** in R3/R4 is exercised only by the synthetic same-value duplicate.
- **Year fold** cannot happen: the controller always passes a single-year window.
- **The Arabic variants** (FillByArabic, the `MonthNameArabic` output) are not compared. D2 makes English the reference, and the Arabic SQL differs only in labels (and, in R3, the sign flip D2 drops).
