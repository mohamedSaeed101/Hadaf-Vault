### The one divergence: R8 percentages (TVF wrong, exact fix below)
- **Legacy.** In `rptIncomeStatmentBranchPeriod.Designer.cs`, the three percentage cells of `GroupFooter4` are bound to `ActivityIncome.PeriodBalance`, `ActivityIncome.LastPeriodBalance` and `ActivityIncome.YearToPeriodBalance` (Designer lines 1003, 1044, 1085). Two facts make them print blank:

  A DevExpress 19.1.3 summary bound to an unfilled table prints nothing (probe below). This is the same copy-paste fault as R3, whose TVF already returns NULL.
- **TVF.** `Acc_IncomeStatementBranchPeriodReport` returns group / report ratios on the `GroupTotal` rows. Example: Faro S1 branch 10101 has 0.113051133003 against a blank on the legacy print.
- **Fix** (`Acc_IncomeStatementBranchPeriodReport.sql`, the `GroupTotal` branch of `ReportRows`):
  - Replace lines 129–131 with `CAST(NULL AS DECIMAL(38,12)),` ×3.
  - Drop line 134, `CROSS JOIN ReportSums s`, which is then unused.
  - In line 29, change the comment to say that R8's percentages are NULL because the legacy cells were bound to `ActivityIncome.*`, which this report never fills.

  This fix was verified in memory on all 13 R8 runs: 13/13 PASS, and the negative control is still detected. Output: scratchpad `fix_*.txt`.
- **Not a numbers issue.** `PeriodPercentage`, `LastPeriodPercentage` and `YearToPeriodPercentage` must then stay unbound or blank in the R8 layout and grid (P3/P4).

### (b) Percentage semantics: group sum ÷ report sum of the bound column, signed
- **Probe** (same build, a `Percentage` summary with `Running = Report` in a group footer):
  - Groups 100+40 and 300+60 print 0.28 and 0.72. That is group share of the report total, not the share of the last row (0.08 / 0.12).
  - With one row negated (−60), they print 0.368421 and 0.631579 = 140/380 and 240/380. So it is a plain signed ratio, with no ABS.
- **R2 and R7.**
  - The TVFs compute `CAST(group SUM AS DECIMAL(19,4)) / NULLIF(CAST(report SUM AS DECIMAL(19,4)), 0)`, over `SubItemBalance` (R2) and over the three ABS balances (R7).
  - They equal the legacy figure to 10 dp (R2, `DECIMAL(19,10)`) and 12 dp (R7, `DECIMAL(38,12)`) in all 26 runs.
  - The print format `{0:0%}` rounds that to whole percent. That is a layout concern.
- **R3 and R8.** The cells are bound to the wrong data member (`ActivityIncome.*`) and print blank.
  - R3 TVF returns NULL: correct.
  - R8 TVF: fix above.
- **Report sum 0.** The TVF returns NULL. The probe did not cover DevExpress's display for a zero total, so the zero-total display is unverified. No run had a zero report total with groups present.

## Method
- **Legacy side ("expected").**
  - SQL: the typed-DataSet `SelectCommand` `CommandText`, read verbatim from the `.xsd` on `AccFlex_ERP` `origin/Master_Stable` and run through `sp_executesql`. Parameter types are the xsd `DbType`s: String with Size 0 becomes `nvarchar(max)`, and Size 1024 (R4, R9) becomes `nvarchar(1024)`.
  - R5: the body of `dbo.Acc_IncomeStatmentWithBranchProd`, plus the `TotalProductionQty` adapter.
  - R9: all six `*PerMonth` adapters, `FillByPeriod` (en) or `FillByPeriodArabic` (ar).
  - Then the C# and Designer maths run in scratch SQL:
    - **R1:** `StatmentOfIncomeReport_BeforePrint`. D(t) = debit − credit. Net = NPBT + `ROUND(ABS(D13), approx)`. The parens flag is set when ≥ 0.
    - **R2/R3:** `GroupHeader1_BeforePrint`.
      - Values that the C# re-parsed are rounded to approx.
      - R3 adds other income raw and signed.
      - GOP = Sum(Cal) per DevExpress group (code).
      - R2 percentage = group / report `SubItemBalance`; R3 is blank.
      - Report-wide rows are NULL when there are no detail rows.
      - Print order: code, then type (R2) or `SubItemBalance` DESC (R3).
    - **R4/R6:** the legacy rows as is. `BranchCode` / `CostCenterNo` (`CAST … NVARCHAR(10)`) is compared with `*SortKey`. Names are compared with `@IsArabic = 1`, where the TVF returns the legacy primary names.
    - **R5:**
      - Floats are compared at `ROUND(…, 6)`. The max raw float difference was 0 on every matched row.
      - `TotalQty` = the SUM over the `TotalProductionQty` adapter.
    - **R7/R8:**
      - Group rows as returned.
      - GOP = Sum `Running = Group` of `Calculate*`.
      - Percentage: R7 = group / report, R8 blank.
      - ReportTotal only when groups exist.
      - TypeTotal = the `Acc_IncomeStatment` rows with type not in (1, 2).
      - NetProfit = the Sum over **all** `Acc_IncomeStatment` rows.
    - **R9:**
      - Pivot view: SUM by (main item, `SubItemName`, month).
      - Per-month GrossProfit = 1 − 2, NetProfitBeforeTax = 1 − 2 − 5 + 3 − 4, NetProfit = before tax + 6.
      - Part `R9T` compares the three C# grand totals (over all rows, including the Taxes NULL-month rows) with the SUM of the TVF's computed rows.
- **New side ("actual").** Each TVF body between `RETURN (` and the final `)`, verbatim, through `sp_executesql` with its own parameter list (defaults stripped).
- **Compare.** Both sides go into identically typed `#E` / `#A` tables (money as `DECIMAL(38,10)`). The checks are:
  - counts
  - EXCEPT both ways
  - the duplicate-aware check
  - SUM per money column, compared as text
  - up to 15 diff rows each way
- **Parts.**
  - R7/R8 run twice: `R78` with the percentages and `R78x` without them.
  - R9 runs twice: `R9` for the pivot cells and computed rows, and `R9T` for the C# totals.
- **DevExpress probes** (scratchpad `dx\SummaryProbe.cs` and `dx2\FillProbe.cs`): compiled with VS 2022 Roslyn `csc` against the GAC `DevExpress.XtraReports.v19.1` 19.1.3.0 and run locally. Output:

GROUP G2 / ROW 300 / ROW 60 / GOP 240 / PCT 0.72     (with G2 type 2 = -60: PCT 0.368421 / 0.631579)
WRONGPCT (summary bound to an empty table): blank

## Quirks exercised (D2), and seen equal on both sides
- **R9 window crossing a year end** (Faro S3, Jun..May, so `Acc_TableNumberRange(6, 5)`): 0 rows on both sides. The C# totals are 0 on both.

- **R9 Taxes NULL-month row** (Nawassy S1 and S2): 1 legacy row and 1 TVF row, Balance 0.
- **R5 per-branch quantity.** It ignores the branch list, while the synthetic total column and `TotalQty` honour it (Faro S2/S3, FHCG S2/S3). Synthetic total rows present: Faro 6–7 per run, FHCG 0–11. Production quantity > 0 on up to 37 rows per run.

  - The type-total year column is always 0.
  - The previous window is shifted by −(1 + DATEDIFF(SECOND)) seconds.
  - Lines with no cost center (R7) or no branch (R8) reach only the type totals and the Net. Faro has 14,977 nature-1 lines with no cost center in 2025; FHCG has 41,201.
- **R2/R3.**
  - The rounded re-parse feeds NPBT and Net.
  - R3 adds other income signed.
  - R3 details sort by `SubItemBalance` DESC.
- **R1** printed Net, in parentheses when ≥ 0. Examples: Faro S1 `10,416,723.6287` is a profit (debit − credit < 0), printed plain. FHCG S2 `(32,182.09)` is ≥ 0, printed in parentheses.

## Data limits (what this cannot prove)
- **R9 sub-item merge:** proven only on the synthetic `#Sub` copy. No db-all tenant has duplicate sub item names.
- **R5 divide by zero:** no tenant has a production detail with quantity 0, so the legacy and TVF divide-by-zero error path is unexercised. Marbo and Nawassy have no production; there R5 compares only the balance and the synthetic total rows.
- **Revised = 1:** only Marbo 2024 has revised lines on income accounts (8 actions); that is set S4. Faro and FHCG have none, so their "not revised" sets equal "all".
- **FHCG S1:** debit equals credit on types 1/2 in that window, so R1 there is all zeros. Its S2 and S3 are non-zero.
- **Empty-string lists** (`''`) were not run. The backend sends NULL, and the legacy MVC binding mapped '' to null.
- **Group codes with punctuation or letters**, where the .NET culture sort and SQL collation could differ, do not occur on these tenants.
- **Zero report total with groups present** (DevExpress percentage display) did not occur.
