# CR-125292 — P4 data parity (legacy MVC SQL vs new TVFs)

- **Server / tenant:** `db-all` / `unp-ali`. **Date:** 2026-10-15. **Run as:** admin, so the legacy security level is 5 and `@SecurityLevel = 5`.
- **Script:** `D:\Hadaf\worktrees\cr125292\parity-125292.sql`. It is outside the repos and not committed. Run it with `sqlcmd -S db-all -d unp-ali -U prouser -C -l 30 -W -s'|' -f 65001 -i parity-125292.sql`, from that folder. `-f 65001` is needed because the file holds Arabic literals.
- **Read-only:** the script only runs SELECTs against `dbo`. The only writes go to session `#temp` tables and table variables. The TVFs were not deployed.
- **Overall: all 8 reports PASS on real data.** There are 56 comparisons, and every one has equal counts, 0 rows in each EXCEPT direction, 0 differences in the duplicate-aware check, and equal sums.

## Method

- **Before (legacy):** the legacy SQL, copied verbatim and run through `sp_executesql` with the typed-DataSet parameter types.
  - Sources:
    - Section c of the vault notes "Legacy - R*.md".
    - R4 `FillEnglish` and `FillArabic`, taken straight from `dsEmployeesSalaryBetweenPeriod.xsd` on `origin/Master_Stable`.
  - R1 and R2 headers, and R2 lines: the script builds the string exactly as the C# `FillByWhere` does, using the verbatim `string.Format` clauses from `rptSalarySignature.cs:54` and `rptEmployeeSalaryDetails.cs:50,62`.
  - R2 and R3 lines: the script passes the header's SalaryId CSV, as the C# does. R3's is passed as `nvarchar(1024)`.
  - R3 "Total Employees Insurance": the C# sum of `IncomeAmount` where `IncomeId = 10`.
- **After (new):** the text of each TVF body between `RETURN (` and `);`, verbatim, run through `sp_executesql` with the TVF's own parameter list.
  - There is one substitution. `PR_EmployeeSummarizedSalariesReportLines` and `PR_EmployeesDetailedSalariesReportLines` semi-join their header TVF, which is not deployed. That call is replaced by the temp table holding the header body's result for the same parameters, which is what the inline TVF expands to.
- **All employees:** the legacy side gets the full `PR_Employee` id CSV, 88 ids and 276 chars, as the old front sent. The new side gets `@EmployeeIds = NULL`.
- **Checks per comparison:**
  - row counts
  - `before EXCEPT after` and `after EXCEPT before`
  - a duplicate-aware check: GROUP BY every compared column with COUNT(*) on both sides, then EXCEPT both ways
  - SUM of every money column, at full 4-dp precision
- **Compared columns:** the legacy column set. Columns the TVFs add (RowNo, EmployeeArabicName, CurrencyNameArabic in R3, SalaryMonth/Year in R1 and R2, and so on) are ignored.
- **Negative control:** the harness does detect differences. The R2 2026-07 case was re-run with the new side at `@SecurityLevel = 1`.
  - The header went from 75 to 74 rows: 1 row in before EXCEPT after, and Total fell from 301,093.93 to 294,718.93.
  - The lines went from 271 to 265 rows.
  - The missing row is employee 4, whose security level is above 1. This is the intended D5 behaviour for non-admin users.

## Synthetic (rolled-back) scenarios: NOT RUN

The coordinator relayed a relaxation, "if data is missing create it", meaning INSERT minimal rows inside `BEGIN TRAN … ROLLBACK`. The session's permission check blocked it ("Modify Shared Resources"). The relaxation arrived through the coordinator agent, not directly from the engineer, so it was not applied. **No row was inserted.**

The last query of the script confirms the starting state: 0 `PR_EmployeeEndWork` rows and 0 deleted runs. The batches below were prepared in the session scratchpad generator (`gen.js`, enabled with `P4_SYN=1`) but are not in `parity-125292.sql`:

- **A, end of work (R6, R8, months 07 and 08, isPost 0 and 1):**
  - Employee 14: `PR_EmployeeEndWork` with LastWorkingDay 2026-07-20, and a detail row with TotalSalary 1234.50, advance 100, purchase 20, penalty 10.
  - Employee 37: LastWorkingDay 2026-08-15, two detail rows (999.25 and 50.00, the second with advance 5).
  - Employee 38: LastWorkingDay 2026-07-10, TotalSalary −5. It should be excluded by `TotalSalary >= 0`.
- **B, second bank account (R3, 2026-07):** a `PR_EmployeeBank` row for employee 5, bank 2, currency 1, account `P4-SYNTH-0002`.
- **C, soft-deleted run (R1–R8, 2026-07):** a copy of `PR_SalaryMain` 21 with `IsDeleted = 1`, copies of salaries 657 and 663 into it, and their 37 detail lines.

These are the untested paths. Each needs either the engineer's direct go-ahead in their own session, or a tenant that has such data:

- R6/R8 end-of-work branch, including the EmployeeId-only join that pulls other months in.
- R3 header duplicated per bank account.
- `IsDeleted` handling: R1 and R2 filter it, R3 to R8 do not.

The TVFs copy the legacy text for all of these: the end-of-work CTEs and CASEs in `PR_DepartmentsMonthlySalariesReport.sql:37-58,81-160,176-189` and `PR_PostedSalariesReport.sql`, the bank join in `PR_EmployeesDetailedSalariesReport.sql:42-44`, and the IsDeleted predicates in `PR_EmployeeSalariesSignatureReport.sql:41` and `PR_EmployeeSummarizedSalariesReport.sql:46`. They are proven only by reading, not by data.
