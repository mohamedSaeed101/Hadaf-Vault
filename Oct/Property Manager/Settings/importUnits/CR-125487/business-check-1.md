## Checked and kept (pass)

- Inheritance from the project (Q8): the screen's own `GetProjectInfoById` maps `ProjectOwnershipId → PropertyOwnershipId`, sales org, cost center, geography, activity, view, ProofOfIncome, street, land number (`GetProjectInfoByIdQuery.cs:45-59`; `property-main-form.component.ts:94-109`). The import copies the same set server-side. **Currency** is the one field the screen does not copy (the query does not return it; the user picks, `property-main-form.component.html:528`); the note's BR-5 lists العملة explicitly, so the spec follows the note. No rule broken; the engineer should know the import differs from the screen here.
- Sales organisation per user: `CreatePropertyCommand.cs:136-151` (`UserSalesOrganization` for `_userSession.UserId`); spec.md:120 keeps it as a row error. Consequence worth knowing: the importing user must be linked to every project's sales org in the file, or those rows fail.
- Leaf-project rule (AC-3), parent-in-same-project (AC-7), investment type within the project's types (AC-4), sale price > 0 for بيع (AC-5): none exists on the screen (`CreatePropertyCommand.cs` checks only existence; the front patches investment types only when the project has more than one, `property-main-form.component.ts:110-113`). The import is stricter, per the note; stricter is allowed, no invariant relaxed.
- Investment type storage: `Pm_PropertyInvestmentType` PK (`PropertyId`, `InvestmentTypeId`) with an FK to `Pm_InvestmentType`; the static ids 1-4 (`InvestmentType.cs:21-24`) must exist in the tenant table, the same as the screen. One id per row is a subset of what the screen allows.
- The spec's risk note on `Property.cs:200` points at the **Update** path. The Create path (`Property.cs:80-81`) never sets `PropertyId`; EF sets the FK through `PropertyConfiguration.cs:25` (`HasMany(...).WithOne().HasForeignKey(x => x.PropertyId)`). The import uses Create, so the phase-5 assertion is cheap insurance, not a fix.
- Serial hierarchy (pcode): `GetNextCodeService.cs:49-73`, root serial = global MAX + 1, child = parent serial + 2-digit counter; the spec saves per row in file order inside one transaction, so a parent on an earlier line exists before its child. `UQ_Pm_Properties_PropertySerial` guards concurrent imports (rollback and retry, as the plan says).
- Add-only (AC-2) and in-file duplicates naming the first line (AC-6): stricter than the screen; `CreatePropertyCommand.cs:263-264` already maps a DB duplicate to `CannotDuplicateNameOrNameSecondLanguage`, so the intent exists. Q7 (name / second name unique) is the same call as CR-125486 Q4.
- Domain rules reused through `Property.Create` → `ValidateProperties` (`Property.cs:272-325`): number, name, second name, type, country, governorate, city, currency, at least one investment type. Spec required flags match; `PropertyNameSecondLanguage` is NOT NULL in `Pm_Properties.sql:7`.
- Blank floor / rooms → 0 (spec.md:89-90) equals the screen's initial value (`properties.service.ts:131-132`); the DB defaults of 1 never apply because the entity always sends a value. `DeliveryPeriodInDays` 0 and ProofOfIncome 1 match `properties.service.ts:154-155`.
- Geography chain: the import copies country / governorate / city / center from the project, so the chain is consistent by construction; the screen's hard-coded 65 / 1 / 1 (`properties.service.ts:361-364`) is a screen bug, correctly out of scope.
- Tenant boundary: single DB per tenant (`accflex-erp-core.md`); PropertyManager, SharedKernel and GeneralLedger contexts share the tenant connection; the log row carries `UserId`. No cross-tenant or cross-branch reach; `Pm_Properties` has no branch column.
- Module id 935 is free (`Module.cs:868` max 933; 934 is CR-125486's). Q9 / Q10 are product choices; no rule touched.
